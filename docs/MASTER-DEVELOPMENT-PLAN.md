## 3. ما هو رقيع؟ وما حدود الإصدار الحالي؟

رقيع أداة لتطبيق رقع نصية على ملفات، خصوصًا ملفات HTML، مع فحص النتائج وحفظها والتحقق منها. سلامة الملف أهم من سرعة إضافة الخصائص.

نحافظ على هذه المسؤوليات الأساسية:

1. **الواجهة:** اختيار الملف، عرض الرقع، المعاينة، وإظهار النتيجة.
2. **هوية الملف:** معرفة الملف الذي فُتح والملف الذي ستُطبَّق عليه العملية فعلًا.
3. **محرك الرقع:** البحث والاستبدال والإضافة والتحقق من شروط الرقعة.
4. **Unicode والإزاحات:** التعامل الصحيح مع العربية والتشكيل والتطبيع ومواقع النص.
5. **الحفظ:** الكتابة المباشرة لملف واحد، أو التعامل مع مجموعة ملفات.
6. **التحقق والاسترجاع:** إعادة قراءة الملفات ومقارنة محتواها، ومحاولة استعادة الأصل عند الفشل.
7. **الأدلة:** حفظ ما حدث، وعلى أي نسخة، وبأي أداة، وبأي نتيجة.

هذا تقسيم للمسؤوليات، وليس ادعاءً بأن التطبيق مقسّم حاليًا إلى سبع وحدات برمجية منفصلة. التطبيق ما زال حزمة HTML كبيرة، وأي إعادة هيكلة مادية له تحتاج إلى مهمة مستقلة.

**هدف الإصدار:** إصدار مستقر يمكن تحديد مصدره وإعادة اختبار سلوكه والتحقق من ملفاته. لا نضيف وظائف جديدة لمجرد زيادة رقم الإصدار أو عدد الرقع.

## 4. قواعد حماية المشروع

هذه القواعد تنطبق على كل خبير وكل مهمة:

- `main` مرجع مستقر: لا تجارب ولا تعديلات مباشرة عليه.
- `RC2` مجمّد: لا تُطبّق عليه رقع التطوير.
- العمل الحالي يجري على فرع المراجعة أو على فرع مهمة مستقل مشتق منه.
- لا يُدمج أي فرع ولا يُنشر إصدار دون قرار صريح.
- لا يُستبدل تقرير قديم؛ تضاف نتيجة جديدة مع الاحتفاظ بالتاريخ.
- لا تُستعاد الأرشيفات تلقائيًا. نفحصها أولًا، ثم نستعيد فقط ما ثبت أنه مطلوب ومفقود.
- لا تُعامل نتائج المحاكاة على أنها اختبارات Native FSA حقيقية.
- لا تُعامل المراجعة الساكنة على أنها اختبار تشغيل.
- لا تنتقل نتيجة اختبار من ملف إلى ملف آخر لمجرد تشابه الاسم أو رقم الإصدار.
- لا تُقبل بصمة منقولة من تقرير قبل مطابقتها مع بايتات الملف الفعلي.
- كل تغيير يجب أن يكون محدودًا، قابلًا للمراجعة، وله طريقة تراجع واضحة.
- لا تُسجّل `PASS` إلا مع أثر يمكن مراجعته؛ ولا تعني `PASS` وحدها اعتماد البوابة.

تبقى تقارير الاختبارات الخام، وسجلات المتصفح، وملفات ZIP، وبيانات البناء في أماكنها المستقلة. لا تنسخها إلى هذه الملفات الثلاثة.

### 5.1 ما الذي يحتويه STATUS.md؟

يجب أن يجيب في صفحة قصيرة عن:

- تاريخ آخر تحديث.
- الفرع وHEAD وTree SHA.
- الحالة العامة للإصدار: `IN_PROGRESS` أو `BLOCKED` أو `READY_FOR_RELEASE` أو `RELEASED`.
- حالة كل بوابة من P0 إلى P8.
- سبب كل `BLOCKED` أو `OPEN`.
- اسم المهمة التالية فقط، والخبير المسؤول عنها إن عُيّن.
- روابط التقارير التي تثبت الحالة.

### 5.2 ما الذي يحتويه BASELINE-MANIFEST.json؟

يُنشأ بأداة قابلة لإعادة التشغيل من الملفات الفعلية، وليس بكتابة البصمات يدويًا. يحتوي على الأقل:

- `repository`, `branch`, `commit`, `tree`, `generatedAt`, `generatorVersion`.
- لكل ملف: `path`, `sizeBytes`, `sha256`, `gitBlobSha`, `role`, `candidateId`, `sourceRef`, `verificationStatus`.
- أنواع الأدوار مثل: `application-source`, `candidate`, `test-runner`, `fixture`, `test-result`, `documentation`, `archive`, `manifest`.
- حالات التحقق مثل: `verified`, `reported-only`, `not-checked`, `mismatch`.

**مهم:** `SHA-256` و`Git Blob SHA-1` قيمتان مختلفتان ولهما غرضان مختلفان. لا تستبدل إحداهما بالأخرى.

يُحتفظ بكل Manifest سابق باسم أو مسار مؤرخ. لا نغيّر لقطة قديمة بصمت.

### 5.3 قواعد الأرشيفات

لكل أرشيف ZIP نسجل: اسمه، حجمه، SHA-256، مكانه الحالي، الالتزام الذي ظهر فيه، هل توجد نسخة أخرى، قائمة محتوياته، وهل يتضمن مصدرًا أو دليلًا فريدًا.

بعد المقارنة فقط نقرر: إبقاء كما هو، استعادة نسخة تاريخية، استخراج محتوى فريد، أو توثيق أنه زائد. لا نحذف نسخة تاريخية لمجرد وجود ملف يحمل الاسم نفسه.

## 7. طريقة قراءة حالات العمل والاختبارات

لتجنب الخلط، نفصل بين **حالة المهمة** و**نوع الاختبار** و**قرار اعتماد البوابة**.

### 7.1 حالة المهمة

| الحالة | معناها ببساطة |
|---|---|
| `NOT_STARTED` | لم تبدأ |
| `IN_PROGRESS` | يجري العمل عليها |
| `OPEN` | ما زالت تحتاج عملًا أو دليلًا |
| `BLOCKED` | لا يمكن إكمالها بسبب عائق محدد |
| `PASS` | معيار المهمة تحقق بالدليل المطلوب |
| `FAIL` | الاختبار نُفذ وأظهر خللًا |
| `SKIPPED` | لم يُنفذ بقرار موثق |

### 7.2 نوع الإثبات

| النوع | ماذا يثبت؟ |
|---|---|
| `REPORTED` | نتيجة منقولة من تقرير أو محادثة؛ لم نتحقق من أصلها الآن |
| `STATIC_REVIEWED` | تمت مراجعة الشفرة أو التصميم دون تشغيل الاختبار |
| `MOCK_TESTED` | الاختبار نُفذ بمحاكاة؛ لا يثبت الوصول إلى ملفات النظام الحقيقية |
| `NATIVE_TESTED` | الاختبار استخدم API ومقابض وملفات حقيقية في بيئة محددة، مع حفظ التقرير |
| `INDEPENDENTLY_VERIFIED` | مراجع مستقل طابق المصدر والأداة والتقرير والأدلة |
| `ACCEPTED` | صاحب قرار البوابة وافق على إغلاقها ضمن نطاق محدد |

**قاعدة:** قد يكون الاختبار `MOCK_TESTED` وناجحًا، بينما البوابة ما زالت `OPEN`. هذا ليس تناقضًا.

## 8. عقد العمل الموحد مع أي خبير

لا تبدأ مهمة قبل أن تحتوي بطاقة التكليف على:

| البند | ما يُكتب فيه |
|---|---|
| الهدف | مشكلة واحدة واضحة والنتيجة المطلوبة |
| المصدر | اسم الفرع وHEAD وبصمة الملف الذي سيُعدّل |
| النطاق | الملفات المسموح تعديلها فقط |
| المحظورات | مثل `main` وRC2 والملفات التاريخية |

| الاختبارات | أسماء الاختبارات وشروط النجاح والفشل |
| الأدلة | الملفات الخام والسجلات والبصمات المطلوبة |
| التراجع | كيف نرجع إلى الحالة السابقة بأمان |
| التسليم | Commit مستقل وتقرير واضح |
| الحكم | `PASS` أو `FAIL` أو `BLOCKED` مع السبب |

### نموذج فحص التسليم لك كمطوّر

- [ ] هل الخبير عمل على الفرع والـ HEAD المحددين؟
- [ ] هل لمس الملفات المسموح بها فقط؟
- [ ] هل قدم Commit ورابطه؟
- [ ] هل قدم ملفات الاختبار الخام، لا ملخص النجاح فقط؟
- [ ] هل البصمات تخص الملفات الموجودة فعلًا؟
- [ ] هل وضح الاختبارات التي لم تُنفذ؟
- [ ] هل توجد طريقة تراجع؟
- [ ] هل بقي `main` وRC2 دون تغيير؟

إذا غاب دليل أساسي، لا تقبل المهمة على أنها مكتملة؛ سجّلها `BLOCKED` أو `OPEN` حسب السبب.

## 9. بوابات التطوير — ماذا نفعل وبأي ترتيب؟

الترتيب التالي هو ترتيب **الاعتماد**. يمكن تنفيذ أعمال مستقلة بالتوازي بعد P0، لكن لا نغلق بوابة اعتمادًا على بوابة سابقة لم تُقبل.

### P0 — تثبيت خط الأساس (أول مهمة)

**الهدف:** معرفة ما الذي يوجد فعلًا في المستودع، ومن أي نسخة، وما بصمته.

**المطلوب:**
1. جرد HEAD والشجرة والالتزامات والملفات.
2. حساب SHA-256 وحجم كل ملف مهم من بايتاته الفعلية.
3. تسجيل Git Blob SHA منفصلًا.
4. جرد الأرشيفات الأربعة ومقارنة الأرشيف الذي حُذف تاريخيًا بنسخته الحالية.
5. تحديد مصادر RC2 وRACEFIX وRACEFIX2 ومجموعات Fixtures وأدوات الاختبار.
6. مراجعة `SHA256SUMS.txt` وتحديد كل اسم مفقود أو بصمة غير مطابقة.
7. إنشاء الملفات الثلاثة: الخطة، الحالة، وManifest.
8. عدم تعديل كود التطبيق في هذه البوابة.

**التسليم:** Manifest مولّد، وSTATUS محدث، وتقرير جرد قصير، وقائمة التناقضات.

**تُغلق P0 عندما:** يمكن لمراجع آخر معرفة الملف الذي يخص كل تقرير، وإعادة حساب بصمته، وتحديد أي ملف غير موجود أو غير مطابق.

### P1 — توحيد الأدلة والمشغّلات

**الهدف:** التأكد من أن كل اختبار شغّل الأداة الصحيحة وعلى المصدر الصحيح.

**المطلوب:**
1. تحديد Runner المستخدم في كل تقرير، وعدم الخلط بين مساعد DevTools وRunner صفحة مستقلة.
2. مراجعة ملف Runner v1.1.8 وبصمته ومصدره ومسار تشغيله.
3. مطابقة Fixture A وB لكل تشغيل باستخدام `fixtureSetId` وبصمة كل ملف.
4. التحقق من أن التقرير يربط كل حالة بـ `caseRunId` فريد.
5. الاحتفاظ بالمحاولات الفاشلة في سجل المحاولات وعدم حذفها من التاريخ.
6. إصلاح أو تحديث Manifest البصمات، دون استبدال التقارير القديمة.

**التسليم:** سجل أدوات موحد، ومصفوفة تربط كل تقرير بالمصدر والـ Runner والـ Fixtures.

**تُغلق P1 عندما:** لا يبقى تقرير مهم مجهول المصدر أو الأداة أو مجموعة الملفات التي اختُبرت.

### P2 — مراجعة RaceFix2 أمنيًا وتقنيًا

**الهدف:** التأكد من أن إصلاح تثبيت هدف الكتابة صحيح في الشفرة، وليس فقط في المحاكاة.

**المطلوب:**
1. مراجعة الكود الذي يثبت مقبض A داخل معاملة الكتابة.
2. التأكد من فصل الملف المحدد في الواجهة عن هدف المعاملة النشطة.
3. مراجعة جميع مسارات الكتابة والتحقق والاسترجاع.
4. فحص القفل ومنع عمليتي كتابة متعارضتين.
5. مراجعة رسائل النجاح والفشل مقابل نتيجة العملية الفعلية.
6. إعادة اختبارات RaceFix2 المحاكية والانحدار على البصمة المحددة.
7. كتابة مراجعة أمنية أولية للمخاطر المكتشفة وكيفية معالجتها.

**التسليم:** تقرير مراجعة مصدر، ونتائج Mock، وقائمة عيوب مرتبة حسب الخطورة، وقرار هل المصدر جاهز لاختبار Native FSA.

**تُغلق P2 عندما:** لا يوجد عيب مانع معروف في مسار المعاملة، وكل نتائج المحاكاة مرتبطة بالبصمة الصحيحة. لا تعني P2 أن Native FSA اجتاز.

### P3 — اعتماد DIRECT-02 / Native FSA

**الهدف:** اختبار RaceFix2 باستخدام منتقي الملفات الأصلي ومقابض ملفات حقيقية، على المصدر نفسه الذي اجتاز P2.

**المطلوب:**
1. تثبيت بصمة المصدر وRunner وFixtures قبل التشغيل.
2. التحقق من استدعاء منتقي الملفات الأصلي ومن الصلاحيات وهوية المقابض.
3. تنفيذ الحالات المحددة: freshness، backup، createWritable، postwrite، write، close، write failure، close-after-commit failure.
4. تضمين اختبار UI فعلي واحد على الأقل، مع توضيح ما أثبته وما لم يختبره.
5. تسجيل ترتيب توقيت تبديل الهدف بالنسبة إلى بدء العملية الأصلية وانتهاء Promise؛ لا تسمّ الاختبار `write-pending` أو `close-pending` إذا كان التبديل قبل استدعاء Native API فقط.
6. التحقق من A وB بعد العملية من المقابض الحقيقية، وحفظ الأحجام والبصمات.
7. مراجعة التقرير بواسطة شخص أو جهة غير منفذة للاختبار.

**تُغلق P3 عندما:** تتطابق الأدلة مع المصدر والأداة والـ Fixtures، وتُغطى الحالات المتفق عليها، وتُحسم التناقضات، ويوافق المراجع على إغلاق DIRECT-02 ضمن نطاقه.

**حد النطاق:** إغلاق DIRECT-02 لا يعني تلقائيًا اعتماد RC3 أو أمن التطبيق كله أو خلوه من كل عيوب الكتابة.

### P4 — إصلاح FOLDER-LOG-01 واعتماد Folder Mode

**الهدف:** أن تصف نتائج الكتابة الجماعية ما حدث بدقة، وألا تسمي فشلًا سابقًا للكتابة «استرجاعًا».

**المطلوب:**
1. تتبع الحالات التي ينتجها `folderRunWriteBatch` والعدادات المرتبطة بها.
2. فصل نتيجة العملية عن نتيجة الاسترجاع.
3. منع `recovered` إذا لم تحدث كتابة فعلية ثم محاولة استرجاع ناجحة.
4. إضافة اختبارات للفشل قبل أول كتابة، والفشل بعد كتابة جزئية، ونجاح الاسترجاع، وفشل الاسترجاع، وفشل إعادة القراءة.
5. التحقق من سلامة ZIP الاحتياطي ومسارات الملفات وأسماء الملفات المكررة.
6. إعادة اختبارات Folder Mode على مرشح محدد البصمة.

**الحالات المقترحة:**

| البعد | القيم |
|---|---|
| نتيجة العملية | `completed`, `cancelled_before_write`, `preflight_failed`, `write_failed`, `verification_failed`, `recovery_failed` |
| نتيجة الاسترجاع | `not_needed`, `not_attempted`, `rollback_verified`, `rollback_failed` |

**قواعد القبول:**
- `no_writes_attempted` عندما يكون عدد الكتابات صفرًا.
- لا يوصف المسار بأنه `rollback_verified` ما لم تحدث كتابة فعلية، ومحاولة استرجاع، ثم تحقق من الملف المستعاد.
- يجب أن تتفق العدادات والحالة النهائية؛ لا تكفي رسالة الواجهة.

**التسليم:** إصلاح محدود، ومصفوفة حالات، وسجلات فعلية أو محاكاة مصنفة بوضوح، وتقرير يثبت اتساق العدادات.

### P5 — إغلاق PR-2 وUnicode

**الهدف:** التأكد من أن البحث الذكي والتعديل لا يفسدان مواضع النص، خصوصًا العربية والنصوص المركبة.

**المطلوب:** ربط كل اختبار ببصمة مرشح محددة، ثم تغطية:

- NFC وNFD.
- الأحرف المركبة والعلامات والتشكيل العربي.
- الإزاحات بوحدات UTF-16 بعد Emoji والمحارف متعددة الوحدات.
- حدود المطابقة ومنع القص داخل مقطع غير آمن.
- `find` و`scope` و`replace` و`replaceAll` و`insertBefore` و`insertAfter`.
- LF وCRLF وCR والنهايات المختلطة.
- نص متعدد الأسطر والمحتوى المجاور.
- التراجع والاسترجاع والانحدار على الحالات السابقة.
- اختبار مضاد مع تعطيل Smart Search عندما يكون ذلك لازمًا لإثبات أن NFC هو سبب النتيجة.
- قياس الأداء على جهاز Android فعلي، إذا كان الأداء على Android ضمن معيار الإصدار.

**التسليم:** مصفوفة حالات فريدة، تقارير خام، بصمة المرشح، ونتيجة مراجعة بشرية.

**تُغلق P5 عندما:** تنجح الحالات الإلزامية على المرشح نفسه، وتُفسر كل حالة غير مختبرة، ولا توجد إزاحة غير موثوقة تسمح بتعديل تخميني.

### P6 — Worker والتخزين والوظائف المتبقية

**الهدف:** إكمال الإصلاحات التي لا تتعلق مباشرة ببوابتي الكتابة وUnicode.

**النطاق:**
- **F3:** المقارنة الثقيلة عبر Worker، وإلغاء المهمة القديمة، وعدم عرض نتيجة جزئية على أنها كاملة.
- **F6:** مسودات اللصق، وحدود العدد والحجم والذاكرة، وسلوك التخزين عند الفشل.
- **F8:** سجل العمليات، والتمييز بين حفظ الذاكرة وحفظ التخزين، وعدم إتلاف بيانات الذاكرة إذا فشل التخزين.
- **F9:** تقرير التحقق الشامل للمجلد؛ ميزة مستقلة لم تُنفذ وفق تقرير الدفعة الأولى.

**التسليم:** بطاقة قبول مستقلة لكل بند، واختبارات انحدار، وقياس الأداء حيث يلزم.

**قاعدة:** لا تجمع F3 وF6 وF8 وF9 في رقعة واحدة كبيرة؛ كل بند له تغيير ونتيجة يمكن مراجعتها منفردة.

### P7 — V3 والاختبارات الشاملة

**الهدف:** تحويل مراجعة V3 الساكنة إلى تشغيل قابل لإعادة الإنتاج.

**مراحل V3 الإلزامية:**

1. `STATIC_REVIEWED`: انتهت مراجعة التصميم والشفرة.
2. `EXECUTION_TESTED`: ثُبتت الاعتماديات، وشُغل الاختبار فعلًا، وحُفظ السجل الخام.
3. `ACCEPTED`: راجع شخص مستقل النتيجة ووافق على إغلاق البوابة.

لا تنتقل إلى مرحلة لمجرد أن المرحلة السابقة بدت سليمة. مراجعة v5 الموجودة حاليًا ساكنة؛ الاختبار لم يُنفذ بحسب سجلها، ولذلك V3 لا تزال `BLOCKED`.

**التسليم:** lockfile معتمد، نسخة الاختبار، إصدار Node والاعتماديات، أمر التشغيل، `v3-rerun.log` الخام، وبصمة المصدر وسجل المراجعة.

### P8 — المراجعة الأمنية النهائية وتجميد الإصدار

**الهدف:** التأكد من سلامة المرشح الكامل قبل أي دمج أو نشر.

**المراجعة الأمنية تشمل:**
- هل يمكن أن تكتب المعاملة في ملف غير الملف الذي اختاره المستخدم؟
- هل يمكن أن يؤدي تبديل الملف أو النقر المتكرر إلى خلط المعاملات؟
- هل يُكتشف التغيير الخارجي قبل الكتابة؟
- هل يجري الاسترجاع فعلًا، وهل يُتحقق منه؟
- هل تعرض الواجهة رسالة تتفق مع النتيجة الحقيقية؟
- هل تُحترم صلاحيات المقابض والملفات؟
- هل يمكن أن تتسرب محتويات الملفات أو بيانات حساسة إلى السجلات؟
- ماذا يحدث إذا أُغلقت الصفحة أو أعيد تحميلها أثناء العملية؟
- هل توجد ثغرات في استيراد الرقع أو التعامل مع المدخلات غير الموثوقة؟

**معايير إصدار v8.0.0:**
1. يوجد ملف مرشح واحد محدد الاسم والحجم وSHA-256.
2. كل تقرير قبول مرتبط ببصمة ذلك المرشح أو لديه تبرير مراجَع لعدم تأثر المسار المختبر.
3. كل البوابات الإلزامية مغلقة، ولا يوجد `BLOCKED` أو `FAIL` مانع.
4. لا توجد ثغرة أمنية حرجة أو عالية غير معالجة أو مقبولة بقرار موثق.
5. الاختبارات القابلة لإعادة التشغيل موثقة بأوامرها واعتمادياتها.
6. توجد نسخة احتياطية وخطة تراجع.
7. توجد موافقة إصدار صريحة منفصلة عن موافقة تنفيذ الرقع.
8. لا يتغير `main` ولا يحدث نشر إلا بعد قرار الإصدار.

**مخرج P8:** سجل إصدار يحتوي رقم النسخة، بصمة الملف، الالتزام، البوابات ونتائجها، المراجعين، قرار الدمج، وقرار النشر.

## 13. قاموس صغير للمصطلحات

| المصطلح | معناه |
|---|---|
| HEAD | الالتزام الذي يشير إليه الفرع الآن |
| Commit | حزمة تغيير محفوظة في Git ولها معرف |
| Tree | لقطة أسماء الملفات ومساراتها في ذلك الالتزام |
| SHA-256 | بصمة لمحتوى الملف؛ أي تغيير في البايتات يغير البصمة عادةً |
| Git Blob SHA | معرف Git لكائن الملف؛ ليس SHA-256 |
| Candidate / مرشح | نسخة قيد الاختبار وليست إصدارًا معتمدًا |
| Fixture | ملف تجريبي مخصص للاختبار، وليس ملف إنتاج |
| Mock | محاكاة لسلوك واجهة أو نظام ملفات؛ لا تثبت الكتابة إلى القرص الحقيقي |
| Native FSA | واجهة المتصفح الأصلية للوصول إلى الملفات ومقابضها |
| Readback | إعادة قراءة الملف بعد الكتابة للتحقق من المحتوى الفعلي |
| Rollback | محاولة إعادة الملف إلى محتواه السابق بعد فشل العملية |
| Gate / بوابة | شرط يجب إثباته قبل السماح بالانتقال إلى المرحلة التالية |
| Regression | إعادة اختبار وظائف قديمة للتأكد أن التغيير الجديد لم يكسرها |

## القرار المقترح لاعتماد الخطة

اعتماد هذه الوثيقة بوصفها **الخطة الرئيسية v1.1** بعد مراجعة مالك المشروع، ثم بدء **P0 فقط**. لا يتضمن هذا الاعتماد إذنًا بتعديل التطبيق أو اعتماد RC3 أو دمج الفرع أو نشر إصدار.

**المبدأ الذي يحكم المشروع:** نفّذ مهمة صغيرة، اختبرها على مصدر معروف، احتفظ بالدليل، ثم اتخذ قرار الانتقال. لا تعتمد على الذاكرة أو الأسماء أو رسائل النجاح وحدها.
